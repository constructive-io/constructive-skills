### DataCapabilities

Per-row required permissions. A profile compiles a person to bits so no policy joins a profiles table; this compiles a row to bits so no policy joins a grant table either — the row carries the mask an actor must hold, and an AuthzEntityMembership policy with mask_column checks it as one bitwise subset test against the SPRT. The mask only narrows: it takes access away from someone membership already lets in, and never grants access to a non-member. Zero requires nothing, which is what an unclassified row defaults to. In direct mode the writer sets the mask and the subset guard bounds it to bits the writer holds; in derived mode it is copied from a mapping row (classification -> mask) by generated triggers, so authors edit one classification instead of every document.

**In a blueprint:** in `tables[].nodes`, as `"DataCapabilities"` or as `{ "$type": "DataCapabilities", "data": { … } }`.

**Parameters**

| Parameter | Type | Default | Required | What it does |
|---|---|---|---|---|
| `field` | string (a column) | `"required_capabilities"` |  | Name of the bit(n) mask column to create on this table. |
| `capabilities` | object |  |  | Selector for the capabilities module whose bit numbering the mask is measured in, e.g. {"scope": "org"}. Every key given must match exactly one module; none or several raises naming the candidates. Required only when the database has more than one. |
| `default` | string[] |  |  | Capability names every row requires unless told otherwise, resolved to a literal mask and baked into the column default. Omitted means a zero mask: requires nothing. |
| `mode` | "direct" or "derived" | `"direct"` |  | Who writes the mask: "direct" the writer, bounded by the subset guard; "derived" the mapping row named by from_column, stamped by generated triggers and hidden from mutations. |
| `from_column` | string (a column) |  |  | Derived mode only: the column on this table naming the mapping row to copy the mask from (e.g. classification_id). |
| `mapping_table` | string |  |  | Derived mode only: table holding one mask per class (e.g. document_classifications). |
| `mapping_key` | string (a column) | `"id"` |  | Derived mode only: column on the mapping table that from_column matches. |
| `mapping_column` | string (a column) |  |  | Derived mode only: the mapping table's own bit(n) mask column. Created when absent, so a classification table needs no DataCapabilities declaration of its own. Defaults to the same name as field. |
| `subset_guard` | boolean | `true` |  | Direct mode only: refuse a write requiring bits the writer does not hold, so nobody can lock a row away from everyone including themselves. Off is for trusted-writer tables only. |
| `entity_field` | string (a column) | `"entity_id"` |  | Direct mode only: the entity column the subset guard's membership check reads. |

### DataHistory

Creates a companion <table>_history table that records a new version row on every INSERT/UPDATE/DELETE via an AFTER trigger. The history table copies the source columns as plain nullable columns with NO keys or constraints, plus a recorded_at timestamp and a history_op column (NEW-append: INSERT/UPDATE store the new row, DELETE stores a tombstone). SELECT policies are cloned from the base table. Optionally range-partitions the history table by recorded_at (pg_partman) with a retention window so history is kept for a while but not forever. Adds an @history smart comment so the Graphile history plugin can expose version queries and restore mutations.

**In a blueprint:** in `tables[].nodes`, as `"DataHistory"` or as `{ "$type": "DataHistory", "data": { … } }`.

**Parameters**

| Parameter | Type | Default | Required | What it does |
|---|---|---|---|---|
| `table_suffix` | string | `"_history"` |  | Suffix for the history table name |
| `recorded_at_field` | string (a column) | `"recorded_at"` |  | Column name for the version timestamp (also the partition key when partitioned) |
| `operation_field` | string (a column) | `"history_op"` |  | Column name recording the operation ('INSERT' \| 'UPDATE' \| 'DELETE') |
| `exclude_fields` | string (a column)[] | `[]` |  | Source columns to omit from the history table (e.g. large jsonb or vector columns). Excluded columns are never created on the history table and never written by the trigger. |
| `copy_mutation_policies` | boolean | `false` |  | Whether to also clone INSERT/UPDATE/DELETE policies (not just SELECT). Default false — the history table is written only by the trigger and exposed read-only through GraphQL. |
| `partitioned` | boolean | `false` |  | When true, range-partition the history table by recorded_at via pg_partman so old partitions can be dropped per the retention window. |
| `partition_interval` | string | `"1 month"` |  | pg_partman partition interval (when partitioned) |

### DataLock

Adds a boolean lock column and guards mutations while a row is locked, so infrastructure rows other things depend on (a bucket a function needs, a route, a resource) are not deleted or edited by accident. Two enforcement modes: step_up requires recent strong verification (via GuardStepUp / require_step_up) for the guarded verbs, while block refuses them outright until the row is unlocked. Clearing the lock is itself step-up guarded, so unlocking is a deliberate, re-authenticated step rather than a silent prelude to deletion.

**In a blueprint:** in `tables[].nodes`, as `"DataLock"` or as `{ "$type": "DataLock", "data": { … } }`.

**Parameters**

| Parameter | Type | Default | Required | What it does |
|---|---|---|---|---|
| `lock_field` | string (a column) | `"locked"` |  | Boolean column holding the lock state |
| `events` | "UPDATE" or "DELETE"[] | `["DELETE"]` |  | Which DML events are guarded while the row is locked. INSERT is not lockable — a row cannot be locked before it exists. |
| `enforcement` | "step_up" or "block" | `"step_up"` |  | How a guarded verb is stopped while locked. step_up requires recent strong verification (needs a provisioned user_auth_module); block refuses the verb outright with ROW_LOCKED until unlocked. |
| `step_up_type` | "password" or "mfa" or "fresh_auth" or "password_or_mfa" | `"fresh_auth"` |  | Verification method satisfying the step-up requirement, for the guarded verbs in step_up mode and for clearing the lock |
| `guard_unlock` | boolean | `true` |  | Require step-up to change the lock column itself, so a locked row cannot be quietly unlocked and then deleted. Redundant (and therefore skipped) in step_up mode when UPDATE is already guarded. |
| `protect_fields` | string (a column)[] | `[]` |  | For a guarded UPDATE, restrict the guard to changes touching these columns. Empty guards the whole row. |
| `default_locked` | boolean | `false` |  | Initial value of the lock column for new rows |
| `min_age` | string | `""` |  | Optional interval (e.g. "24 hours"); in step_up mode the guard only fires for rows older than this, so freshly created rows stay easy to clean up. Empty guards rows of any age. |

## Relation nodes

### RelationBelongsTo

Creates a foreign key field on the source table referencing the target table. Auto-derives the FK field name from the target table name using inflection (e.g., projects derives project_id). delete_action is required and must be explicitly provided by the caller.

**In a blueprint:** in `relations[]`, as `{ "$type": "RelationBelongsTo", … }` with the parameters at the top level. Required: `delete_action`. The backend sets `source_table_id` and `target_table_id` from the two ends.

**Parameters**

| Parameter | Type | Default | Required | What it does |
|---|---|---|---|---|
| `field_name` | string (a column) |  |  | FK field name on the source table. Auto-derived from target table name if omitted (e.g., projects → project_id) |
| `delete_action` | "c" or "r" or "n" or "d" or "a" |  | yes | FK delete action: c=CASCADE, r=RESTRICT, n=SET NULL, d=SET DEFAULT, a=NO ACTION. Required. |
| `is_required` | boolean | `true` |  | Whether the FK field is NOT NULL |
| `scope_fields` | string (a column)[] |  |  | Columns both tables carry that the referenced row must share with the referencing row (e.g. ["entity_id"], or ["project_id"] for a stage of the same project). Adds a hidden composite FK (field_name, ...scope_fields) -> target (id, ...scope_fields) plus the target unique key it needs, so a row cannot point at another scope's row even when it knows the id. |

**Rules**

- Give exactly one of `source_table`, or `source_module`.
- Give exactly one of `target_table`, or `target_module`.

### RelationManyToMany

Creates a junction table between source and target tables with auto-derived naming and FK fields. The trigger creates a bare table (no implicit DataId), adds FK fields to both tables, optionally creates a composite PK (use_composite_key), then forwards all security config to secure_table_provision as-is. The trigger never injects values the caller did not provide. Junction table FKs always CASCADE on delete.

**In a blueprint:** in `relations[]`, as `{ "$type": "RelationManyToMany", … }` with the parameters at the top level. Nothing is required beyond the two ends. The backend sets `source_table_id` and `target_table_id` from the two ends.

**Parameters**

| Parameter | Type | Default | Required | What it does |
|---|---|---|---|---|
| `junction_table_id` | string |  |  | Existing junction table to use. If uuid_nil(), a new bare table is created |
| `junction_table_name` | string |  |  | Junction table name. Auto-derived from both table names if omitted (e.g., projects + tags derives project_tags) |
| `source_field_name` | string (a column) |  |  | FK field name on junction for source table. Auto-derived if omitted (e.g., projects derives project_id) |
| `target_field_name` | string (a column) |  |  | FK field name on junction for target table. Auto-derived if omitted (e.g., tags derives tag_id) |
| `use_composite_key` | boolean | `false` |  | When true, creates a composite PK from the two FK fields. When false, no PK is created by the trigger (use nodes with DataId for UUID PK). Mutually exclusive with nodes containing DataId. |
| `nodes` | object[] |  |  | Array of node objects for field creation on junction table. Each object has a $type key (e.g. DataId, DataEntityMembership) and optional data keys. Forwarded to secure_table_provision as-is. Empty array means no additional fields. |
| `grants` | object[] |  |  | Unified grant objects for the junction table. Each entry is { roles: string[], privileges: string[][] }. Forwarded to secure_table_provision as-is. Default: [] |
| `policies` | object[] |  |  | RLS policy objects for the junction table. Each entry has $type (Authz* generator), optional data, privileges, policy_role, permissive, policy_name. Forwarded to secure_table_provision as-is. Default: [] |

**Rules**

- Give exactly one of `source_table`, or `source_module`.
- Give exactly one of `target_table`, or `target_module`.

**In a blueprint:** in `relations[]`, as `{ "$type": "RelationSpatial", … }` with the parameters at the top level. Required: `name`, `operator`, `source_field` and `target_field`. The backend sets `source_table_id`, `source_field_id`, `target_table_id` and `target_field_id` from the two ends.

| `operator` | "st_contains" or "st_within" or "st_intersects" or "st_covers" or "st_coveredby" or "st_overlaps" or "st_touches" or "st_dwithin" |  | yes | PostGIS spatial predicate. One of the 8 whitelisted operators. st_dwithin requires param_name. |
| `param_name` | string |  |  | Parameter name for parametric operators (currently only st_dwithin, which needs a distance argument). Must be NULL for all other operators. Enforced by table CHECK. |

**Rules**
